Team Git Workflow

How the Laag ta bAI team branches, pushes, opens pull requests, and promotes code from local to staging to production. This applies to both laag-ta-bai-frontend and laag-ta-bai-api.

The flow at a glance

Yes, there is a staging environment. The development branch is staging. Every merge into development auto-deploys to the staging site, where the team and QA test it. main is production and only changes through a release PR plus a manual approval. Nobody pushes directly to development or main.

Daily steps for every developer

  1. One-time: clone and install

    git clone https://github.com/VersionControlSD3/laag-ta-bai-api.git
git clone https://github.com/VersionControlSD3/laag-ta-bai-frontend.git

cd laag-ta-bai-api      && npm ci && cp .env.example .env
cd ../laag-ta-bai-frontend && npm ci && cp .env.example .env.local

    Ask the team lead for org access first. You need write access to push branches. Never commit .env files.

  2. Start from the latest development

    git switch development
git pull origin development
git switch -c feature/scan-retake-hints     # or fix/chat-scroll, docs/setup-guide

    Name branches feature/…, fix/…, docs/… or chore/…, followed by a few words. Use one branch per task, ideally linked to a ClickUp task.

  3. Work, run the app, commit in small steps

    npm run dev                                   # run it (API on :3000, frontend on :5173)
git add -A
git commit -m "feat(scan): show retake tips on low confidence"

    Use Conventional Commits: feat:, fix:, docs:, test:, refactor:, chore:.

  4. Check locally before pushing

    # frontend
npm run lint && npm test && npm run build
# api
npm run lint && npm run lint:openapi && npm run typecheck && npm test && npm run build

    These are the same steps CI runs. If they pass on your machine, they will almost always pass on GitHub.

  5. Push your branch

    git push -u origin feature/scan-retake-hints

    GitHub prints a link to open a pull request.

  6. Open a pull request into development

    On GitHub, set base: development ← compare: your branch. Fill in the PR template, add screenshots for UI changes, and request a reviewer. With the GitHub CLI:

    gh pr create --base development --fill --reviewer <teammate>

  7. CI and review

    The "Lint, test and build" check must be green and one teammate must approve. If you get review comments, push more commits to the same branch and the PR updates itself.

  8. Squash-merge, then clean up

    # after merging on GitHub (the branch is auto-deleted there)
git switch development && git pull origin development
git branch -d feature/scan-retake-hints

    Your change is now on staging once the deploy finishes. Test it there.

Pull request rules

TargetFeature and fix PRs go into development. Only release and hotfix PRs go into main.
SizeOne task per PR. Keep it small enough to review in about 15 minutes. Split big features.
ChecksCI must pass. A failing check blocks the merge (SPMP 3.2).
Review1 approval for development, 1 approval plus a QA sign-off for releases to main.
Merge styleSquash-merge, so development keeps one clean commit per PR.
NeverCommit secrets or .env files, force-push to shared branches, or push directly to development/main.

Keeping your branch up to date

If development moved on while you were working, or GitHub says there are conflicts:

git fetch origin
git merge origin/development          # fix any conflicts, then:
git add -A && git commit
git push

Release to production & hotfixes

Regular release (e.g. end of a sprint)

  1. QA confirms that staging works (scan, chat, profile, plus the features in the release).
  2. Open a PR from development → main titled like release: sprint 3, and list what is included.
  3. CI passes, the PM or lead approves, then merge with a merge commit (not squash), so main and development stay in sync.
  4. The Deploy workflow starts and waits. A required reviewer opens Actions → Deploy → Review deployments → Approve.
  5. Production is live. If something breaks, roll back in Vercel → Deployments → Promote the previous one, then fix forward through a PR.

Hotfix (production is broken now)

git switch main && git pull origin main
git switch -c hotfix/login-crash
# fix, commit, push
gh pr create --base main --fill            # review, merge, approve the deploy
# then bring the fix back to development:
git switch development && git pull origin development && git merge origin/main && git push

Changes that touch both frontend and API

The API's openapi.yaml is the contract. When a feature needs a new or changed endpoint:

  1. API first. Open a PR in laag-ta-bai-api that changes the route and openapi.yaml together. Prefer adding fields or routes over changing existing ones.
  2. Frontend second. Open a PR in laag-ta-bai-frontend that updates src/api/types.ts and the UI. Link the API PR in the description.
  3. Merge the API PR first, so staging has the endpoint before the UI calls it.
  4. For database changes, add a new migration in supabase/migrations/ in the API PR. Never edit a migration that has already been applied.

One-time admin setup (org owner or lead)

1. Give the team access

GitHub → VersionControlSD3 → Teams → create a team (e.g. laag-ta-bai-devs) → add members → Repositories → add both repos with Write access. Leads get Maintain.

2. Protect main and development

In each repo, go to Settings → Rules → Rulesets → New branch ruleset (or Settings → Branches):

  • main: require a pull request with 1 approval and dismiss stale approvals. Require the status check Lint, test and build. Require conversation resolution. Block force pushes and deletions.
  • development: require a pull request with 1 approval and the same status check. Block force pushes.
  • Settings → General: allow squash merging (for features) and merge commits (for releases), and turn on Automatically delete head branches.
3. Create the staging and production environments

Settings → Environments → staging (deployment branch: development) and production (deployment branch: main, required reviewers: the PM or lead).

4. Connect Vercel and Supabase, then turn deploys on
  • Create two Supabase projects, laag-ta-bai-staging and laag-ta-bai-prod, and apply the migrations to each (npx supabase link then npx supabase db push).
  • Create a Vercel project per repo. Set the environment variables for Preview (staging) and Production (see each repo's docs/ci-cd.md).
  • Add the secrets VERCEL_TOKEN, VERCEL_ORG_ID and VERCEL_PROJECT_ID to both GitHub environments. For the API, also add SUPABASE_ACCESS_TOKEN, SUPABASE_PROJECT_REF and SUPABASE_DB_PASSWORD if migrations should run automatically.
  • Add the repository variable DEPLOY_ENABLED=true. Optionally add VERCEL_STAGING_ALIAS (e.g. laag-ta-bai-staging.vercel.app) for a stable staging URL.

FAQ

CI failed on my PR. What now?

Open the PR, go to Checks → Lint, test and build, and read the first red step. Reproduce it locally with the commands in step 4, fix it, commit, and push. CI re-runs by itself.

I accidentally committed to development locally. 
git switch -c feature/my-work      # your commits move with you
git switch development && git reset --hard origin/development
git switch feature/my-work && git push -u origin feature/my-work
I committed a secret.

Tell the lead immediately and rotate the key in Supabase, Google or Vercel. Deleting the commit is not enough, because it stays in history and forks.

Where do I test on my phone?

Use the staging URL once deploys are on. Camera and GPS need HTTPS, which localhost over Wi-Fi doesn't provide.

Can I work without Supabase or Gemini keys?

Yes. The API's memory mode gives you seed landmarks, stub AI replies, and a "dev traveler" login. Most UI and logic work needs nothing else.
